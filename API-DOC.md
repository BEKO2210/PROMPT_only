# API-DOC — API-Dokumentations-Bundle (verkaufbares Deliverable)

Produces three artefacts from existing API code: an OpenAPI 3.1
specification, a Postman / Bruno collection, and a human-readable
Markdown reference with multi-language code examples. Almost every
startup has an undocumented or under-documented API — this is one of the
easiest sells in the catalogue.

**Realistic engagement price: €1 000 – 5 000 per API surface.**

---

## How to use

Paste the block below, then on the next line:

    SCOPE: <which API — path prefix, version, public-facing or internal>
    BASE_URL: <production base URL the examples should use>
    AUTH: <how clients authenticate — bearer, API key header, OAuth, …>
    CLIENT: <client name — optional>

## The prompt (copy from here)

```
You are producing an API Documentation Bundle from existing code. Three
artefacts are deliverables: §7 OpenAPI YAML, §8 Postman JSON, §9
Markdown reference. All three must describe the SAME endpoints with the
SAME schemas — drift between them destroys the bundle's value.

1. SCOPE
   Restate scope: API name, version, path prefix, framework (FastAPI /
   Express / Spring / Rails / Django REST / Gin / Axum / …), language,
   commit SHA. Note public vs internal status — internal APIs are
   documented differently (less defensive examples, more candid error
   modes).

2. INVENTORY
   Discover every endpoint in scope. Per endpoint, capture:
     - method (GET / POST / PUT / PATCH / DELETE / …)
     - path (with path parameters templated: `/users/{id}`)
     - handler file:line (so a reader can find the source)
     - one-sentence purpose (from docstring, function name, or inferred
       from code — if inferred, note `[inferred]`)
   Cap discovery at 30 tool calls; if more endpoints exist, ship what
   you have and note the gap.

3. SCHEMAS
   For every endpoint, derive request and response schemas from code:
     - request: path params, query params, headers, body (JSON Schema)
     - response: per status code, body shape
     - referenced models extracted to `components.schemas` (DRY)
   Sources: framework decorators (FastAPI Pydantic, Spring annotations),
   declared models (Mongoose schemas, ActiveRecord, Prisma), or careful
   inspection of handler code.

4. AUTH & RATE LIMITS
   - Authentication scheme per endpoint (or globally if uniform).
     Document as OpenAPI `securitySchemes`.
   - Authorisation rules visible in code (role checks, ownership checks)
     — document in the endpoint description.
   - Rate-limiting if implemented (middleware, decorator) — document
     headers and limits.

5. EXAMPLES
   For each endpoint, provide a realistic request example in three
   languages, using the AUTH and BASE_URL from input:
     - cURL
     - Python (requests)
     - JavaScript (fetch)
   Plus one realistic response example per documented status code.
   Use plausible business data (no `foo`/`bar`).

6. ERRORS
   Document the error response envelope (standard problem+json? custom?)
   and every error code an endpoint can return that is NOT a generic
   500. Include validation errors with example payloads.

7. OPENAPI YAML  ← deliverable (a)
   Single OpenAPI 3.1 document between markers. Required: openapi,
   info, servers, paths, components.schemas, components.securitySchemes,
   security. Validates against the OAS 3.1 schema.
   --- OPENAPI YAML START ---
   openapi: 3.1.0
   info: { ... }
   ...
   --- OPENAPI YAML END ---

8. POSTMAN COLLECTION  ← deliverable (b)
   Postman Collection v2.1 JSON. One folder per resource, one request
   per endpoint, environment variables for `{{baseUrl}}` and
   `{{authToken}}`. Include sample request body from §5.
   --- POSTMAN JSON START ---
   { "info": { ... }, "item": [ ... ] }
   --- POSTMAN JSON END ---

9. MARKDOWN REFERENCE  ← deliverable (c)
   --- REPORT START ---
   # <API name> — Developer Reference
   **Version:** <…>   **Base URL:** <…>   **Date:** <…>

   ## Getting Started               (auth setup in 3 steps)
   ## Authentication                (§4)
   ## Conventions                   (versioning, pagination, errors)
   ## Endpoints                     (grouped by resource)
       ### <METHOD> <path>
       Purpose. Auth. Path params. Query params. Body schema.
       Response schemas. cURL example. Python example. JS example.
       Errors.
   ## Error Reference               (§6)
   ## Rate Limits                   (§4)
   ## Changelog placeholder         (for future versions)
   ## Limitations                   (§10, verbatim)
   --- REPORT END ---

10. LIMITATIONS & DISCLAIMER  (mandatory, verbatim with substitutions)
    "This documentation bundle was generated by an AI agent from static
     analysis of the codebase at commit <SHA> on <date>. Schemas are
     inferred from code and may not match runtime behaviour if dynamic
     serialisation, middleware, or response wrappers transform payloads
     before they leave the server. No contract testing was performed
     against the live API. Examples use plausible but synthetic data;
     real responses may include fields not represented here. For
     guaranteed accuracy, this bundle should be paired with contract
     tests (Schemathesis, Dredd) run against the staging environment
     before publication."

HARD RULES
- The endpoint set in §7, §8, and §9 must be IDENTICAL. After
  generating all three, do one reconciliation pass: any endpoint in
  one artefact must be in all three.
- Every schema field type comes from code evidence. Never invent fields.
- Examples use the actual auth scheme from §4 and the actual base URL
  from input — not `https://api.example.com`.
- Code examples must be runnable: copy-paste into a terminal /
  notebook / browser and they execute (against a real server with
  valid auth).
- Respond in the same language as the SCOPE input. Code examples
  remain English (idiomatic in their language).

SCOPE:
```

## What the buyer gets

Three files: `openapi.yaml` (import into Stoplight, Swagger UI, ReadMe.io,
Redocly), `<api>.postman_collection.json` (their devrel team distributes
to customers), and `API_REFERENCE.md` (renders on GitHub / Confluence /
their docs site). Each artefact stands alone; together they let any
external developer integrate without asking the client's team a single
question.
