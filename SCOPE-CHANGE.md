# SCOPE-CHANGE — Change Order für Mehrleistung (interner Hebel)

When a client asks for "just one small thing" outside the signed
scope, the answer is either "no" (kills relationship) or "yes" (kills
margin) — unless you have a change-order process. This generates a
professional change-order document the client signs before the work
starts.

**Leverage value: every change order captured = 10–40% upsell on
existing engagements. Most consultants leave this on the table.**

---

## How to use

Paste the block below, then on the next line:

    ORIGINAL_ENGAGEMENT: <signed proposal reference + summary>
    REQUESTED_CHANGE: <what the client is now asking for>
    REQUEST_SOURCE: <email / call / Slack — paste the actual ask>
    YOUR_RATE: <your day-rate or fee structure>
    REQUESTING_CONTACT: <name + role of who's asking>

---

## The prompt (copy from here)

```
You are producing a change-order document. The §6 DOCUMENT is the
deliverable, sent within 48 hours of the §REQUESTED_CHANGE so the
relationship momentum is preserved. Three rules:

(1) FRAME AS YES, NOT NO. Default tone: "Here's how we can make
    that happen." Then quote scope, cost, timeline impact.
(2) ITEMISE IMPACT. Show what changes in scope, cost, AND timeline.
    Hiding the timeline impact creates trust loss when delays
    surface later.
(3) MAKE APPROVAL FRICTIONLESS. One signature line, one button,
    one reply. Long approval processes lose the moment.

1. CLASSIFY THE REQUEST
   - SCOPE EXPANSION: new deliverable not in original scope
   - SCOPE DEEPENING: more detail / depth on existing deliverable
   - TIMELINE COMPRESSION: faster delivery of same scope
   - SCOPE RESHAPING: replace one item with another (often net-zero
     cost, but timeline / risk shift)
   - CLARIFICATION (NOT A CHANGE): scope was ambiguous; client
     wants what they thought was included. Handle carefully —
     this is reputation territory.
   Classification drives both pricing approach and tone.

2. SCOPE DELTA  (precise)
   - What's being ADDED (specific deliverables / activities)
   - What's being REMOVED (if anything — to avoid double-charging)
   - What's being CHANGED (transformation of existing scope)
   Cite the original PROPOSAL line items where applicable.

3. EFFORT ESTIMATE
   - Person-hours by activity (best / likely / worst)
   - Skills required (if different from original team)
   - Dependencies (does this need new client input?)

4. PRICING
   - Approach: fixed-fee for the change (preferred) / hourly
     against a not-to-exceed cap / per-deliverable
   - Anchor: state value before number. "This adds <outcome>;
     the investment is <€>."
   - Payment terms: standard (50% on signature / 50% on delivery)
     or align with original engagement billing
   - Currency, VAT (consistent with original engagement)
   - Discount note: if you're discounting (e.g. existing-client
     courtesy), name it so the client knows it's a goodwill move
     — never silent discounts

5. TIMELINE IMPACT
   - Does this delay any existing milestones? (Yes/No, by how much)
   - Can the change be parallel-streamed (no impact) or serial
     (impact)
   - New target completion for the change scope
   - Updated overall engagement completion if affected

6. DOCUMENT  ← the deliverable
   --- DOCUMENT START ---
   # Change Order #<N>: <Short title>
   **Engagement:** <ORIGINAL_ENGAGEMENT>
   **Date:** <…>   **Reference:** CO-<YYYY>-<NNN>
   **Requesting contact:** <…>
   **Valid until:** <14 days from issuance>

   ## Summary
   You asked for: <one-sentence restatement of REQUESTED_CHANGE>.
   Here's how we can make that happen.

   ## What changes in scope
   **Added:**
   - <item 1>
   - <item 2>
   **Removed / replaced:**
   - <if applicable>
   **What stays the same:**
   - <reassure that the original engagement is intact>

   ## What this adds
   **Investment:** <€X> (or hourly with NTE cap)
   **Payment terms:** <…>
   **Effort estimate:** <best / likely / worst person-hours or
   days>

   ## Timeline
   **Delivery of this change:** <date>
   **Impact on original engagement:** <none / X-day delay to
   milestone Y>

   ## To approve
   Reply with "Approved" to this email, OR sign below:

   Signature: ___________________   Date: __________
   Name / Role: <REQUESTING_CONTACT>

   We'll start within 2 business days of approval.

   ## Standard terms
   This change order is governed by the terms of the original
   engagement agreement dated <…>. Out-of-scope requests after
   this change require a further change order.
   --- DOCUMENT END ---

7. ESCALATION PATH  (for the consultant's record)
   - If client pushes back on price: alternative scopes that could
     hit a lower price point
   - If client wants it included for free: language that holds
     the line without breaking relationship
   - If client refuses to sign: log the request, decline the work,
     keep the relationship

HARD RULES
- Tone is "yes, here's how" — never "that's out of scope" without
  immediately offering a path.
- Itemise scope + cost + timeline impact. Hiding one creates trust
  loss.
- Approval is frictionless: one reply or one signature.
- If §1 classifies the request as CLARIFICATION (not a change),
  the document is a no-cost confirmation, not a change order.
  Don't bill for what was implicitly included.
- Respond in the language of the REQUEST_SOURCE.

ORIGINAL_ENGAGEMENT:
REQUESTED_CHANGE:
REQUEST_SOURCE:
YOUR_RATE:
REQUESTING_CONTACT:
```

## What you get

A change order ready to send. Most consultants lose 10–30% of
revenue per engagement by absorbing scope creep — this captures it
without straining the relationship. The "yes, here's how" tone is
critical: clients pay for change orders that feel collaborative; they
fight change orders that feel adversarial.
